# Git Commit スキル

変更内容を分析し、適切な gitmoji + Conventional Commits 形式の日本語コミットメッセージを生成してコミットを実行する。

## コミットメッセージ形式

```
<gitmoji> <type>(<scope>): <subject>

<body>
```

### 各要素の説明

- **gitmoji**: 変更の種類を視覚的に示す絵文字（下記マッピング参照）
- **type**: Conventional Commits のタイプ
- **scope**: 変更の影響範囲（省略可。コンポーネント名、モジュール名など）
- **subject**: 変更内容の要約（命令形・体言止め、50文字以内）
- **body**: 変更の理由や詳細（省略可。「なぜ」を中心に書く）

### gitmoji × type マッピング

| gitmoji | type     | 用途                             |
| ------- | -------- | -------------------------------- |
| ✨      | feat     | 新機能の追加                     |
| 🐛      | fix      | バグ修正                         |
| 🔥      | remove   | コード・ファイルの削除           |
| 📝      | docs     | ドキュメントの変更               |
| 💄      | style    | UI・スタイルの変更               |
| ♻️      | refactor | リファクタリング（機能変更なし） |
| ⚡      | perf     | パフォーマンス改善               |
| ✅      | test     | テストの追加・修正               |
| 🔧      | chore    | 設定ファイル・ビルド関連の変更   |
| ➕      | deps     | 依存関係の追加                   |
| ➖      | deps     | 依存関係の削除                   |
| ⬆️      | deps     | 依存関係のアップグレード         |
| 🔀      | merge    | ブランチのマージ                 |
| 🚚      | move     | ファイルの移動・リネーム         |
| 🗃️      | db       | データベース関連の変更           |
| 🔒      | security | セキュリティ修正                 |
| 🚀      | deploy   | デプロイ関連                     |
| 💚      | ci       | CI/CDの修正                      |
| 🎨      | format   | コードフォーマットの改善         |
| 🏗️      | arch     | アーキテクチャの変更             |

## コミット手順

以下の手順を **必ずこの順番で** 実行する。

### 1. 変更内容の確認

並列で以下を実行：

```bash
git status          # 変更ファイルの一覧
git diff            # ステージされていない変更の差分
git diff --cached   # ステージ済みの変更の差分
```

### 2. 変更の分析とメッセージ生成

差分を読み、以下を判断する：

- **type**: 変更の種類は何か（feat, fix, refactor, ...）
- **scope**: 変更の主な対象は何か（コンポーネント名、モジュール名など）
- **subject**: 変更内容を一言で要約すると？（「なぜ」ではなく「何を」）
- **body**: 「なぜ」この変更が必要か？（自明な場合は省略）

#### subject の書き方ガイド

- 体言止めまたは命令形で書く（「〜した」「〜しました」は使わない）
- 50文字以内に収める
- 具体的に書く。「スタイルの改善」ではなく「記事一覧のカード間マージンを統一」のように

良い例：

- `✨ feat(auth): ログイン画面にソーシャル認証を追加`
- `🐛 fix(api): ページネーションのオフセット計算を修正`
- `♻️ refactor(hooks): useAuth の状態管理を useReducer に移行`
- `🔧 chore: ESLint の unused-imports ルールを有効化`
- `💄 style(header): モバイル時のナビゲーションメニューのレイアウトを調整`

悪い例：

- `✨ feat: 機能を追加しました` （何の機能か不明、「しました」は不要）
- `🐛 fix: バグ修正` （何のバグか不明）
- `♻️ refactor: コードを改善` （何をどう改善したか不明）

### 3. コミットメッセージの確認

生成したコミットメッセージを **AskUserQuestion ツール** でユーザーに提示し、承認を得てからコミットする。

- 選択肢としてコミットメッセージ全文を提示し、「このままコミット」「修正する」などの選択肢を用意する
- ユーザーが承認するまで絶対にコミットを実行しない

### 4. ステージングとコミット

ステージされていない変更がある場合は、適切なファイルをステージする。

- `.env`、認証情報、シークレットなどの機密ファイルは **絶対にステージしない**。見つけた場合はユーザーに警告する
- 論理的にまとまりのある変更単位でステージする
- `git add -A` や `git add .` は使わず、ファイルを個別に指定する

コミットメッセージは HEREDOC で渡す：

```bash
git commit -m "$(cat <<'EOF'
✨ feat(scope): subject の内容

body の内容（必要な場合）
EOF
)"
```

### 5. 確認

コミット後に `git status` で結果を確認し、ユーザーに報告する。

## 注意事項

- 変更がない場合は空コミットを作らず、ユーザーにその旨を伝える
- 複数の論理的な変更がある場合は、分割コミットを提案する
- `--amend` は使わない（ユーザーが明示的に指示した場合を除く）
- `--no-verify` は使わない（フックを尊重する）
- フックが失敗した場合は原因を調査し、修正してから新しいコミットを作る
- リモートへの push はユーザーの明示的な指示がない限り行わない
